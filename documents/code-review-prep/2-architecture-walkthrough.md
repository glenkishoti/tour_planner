# Backend Architecture Walkthrough — TourPlanner

This is your map of the backend so you can explain any part on demand. It follows a request from the wire down to the database and back, then covers the cross-cutting pieces (security, mapping, the external API, persistence).

**Stack:** Spring Boot 3.2.5, Java 21, Spring Web (REST), Spring Security + JWT (jjwt 0.12.5), Spring Data JPA / Hibernate, PostgreSQL, Lombok, Log4j2, Apache HttpClient 5 (for the OpenRouteService calls), packaged with Maven and Docker.

---

## The big picture: a layered (n-tier) architecture

```
HTTP/JSON
   │
   ▼
Controller layer   ── REST endpoints, HTTP concerns, @Valid, exception handlers
   │  (DTOs in/out)
   ▼
Service layer      ── business logic, ownership checks, @Transactional, orchestration
   │                         │
   │                         ▼
   │                  Integration layer (OpenRouteServiceClient → external routing API)
   ▼
Repository layer   ── Spring Data JPA interfaces, queries
   │
   ▼
PostgreSQL         ── users, tours, tour_logs
```

The rule that keeps it clean: **dependencies point downward only.** Controllers know about services; services know about repositories and the ORS client; nothing points back up. Entities never leave the service layer — controllers speak DTOs. This is exactly the layering shown in `documents/architecture.md`.

## Layer 1 — Controllers (presentation)

Five REST controllers, each a thin adapter that maps HTTP to a service call:

- `AuthController` — `POST /api/auth/register`, `POST /api/auth/login` (the only public endpoints)
- `TourController` — CRUD on `/api/tours`, plus image upload/download
- `TourLogController` — CRUD on `/api/tours/{tourId}/logs` (logs are nested under a tour)
- `SearchController` — `/api/search/tours`, `/tour-logs`, `/tours/advanced`
- `StatisticsController` — `/api/statistics` and `/api/statistics/tour/{id}`
- `ImportExportController` — JSON export/import of tours

Controllers do four things only: declare the route, validate input (`@Valid`), call one service method, and wrap the result in a `ResponseEntity` with the right status code (e.g. `201 Created` on POST). They contain no business logic. Each currently declares its own `@ExceptionHandler` methods (the audit recommends consolidating these into one global handler).

## Layer 2 — Services (business logic)

This is where the real work lives, and every service is `@Transactional` so each call runs in one DB transaction (read-only where nothing is written).

- `AuthService` — register (uniqueness checks + BCrypt hash) and login (verify password, mint JWT).
- `TourService` — tour CRUD; on create/update it calls the ORS client to fill in distance/time when the user didn't provide them.
- `TourLogService` — log CRUD, always scoped to a tour the current user owns.
- `SearchService` — simple text search (delegated to DB queries) and an advanced in-memory filter.
- `StatisticsService` — aggregates tours/logs into overall, per-tour, monthly, and per-transport-type stats.
- `ImportExportService` — serializes tours+logs to JSON and rebuilds them on import (uses a Jackson `ObjectMapper` with the JSR-310 time module).

Two patterns to point out here:
1. **Ownership check on every operation.** Each service resolves the logged-in user (`getCurrentUser()` reads the username from the `SecurityContext`) and every repository call is `findByIdAndUserId(...)`. A user physically cannot touch another user's data, even by guessing an ID.
2. **Orchestration.** `TourService.createTour` is the clearest example: resolve user → map DTO to entity → call external routing API → persist → map back to a response DTO.

## Layer 3 — Repositories (data access)

Three Spring Data JPA interfaces — you write the method signature, Spring generates the query:

- `UserRepository` — `findByUsername`, `findByEmail`, `existsByUsername`, `existsByEmail`.
- `TourRepository` — `findByUserId`, `findByIdAndUserId`, `existsByIdAndUserId`, plus a `@Query` full-text `searchTours`.
- `TourLogRepository` — owner-scoped finders plus a `@Query` `searchTourLogs` that joins through `tour.user.id`.

Derived query methods cover the common cases; the two custom `@Query` (JPQL) methods handle case-insensitive `LIKE` search across multiple columns.

## Layer 4 — Database

PostgreSQL with three tables: `users`, `tours`, `tour_logs`. Relationships:
- `User 1—* Tour` (`tour.user_id`, lazy)
- `Tour 1—* TourLog` (`tour_logs.tour_id`, lazy, `cascade = ALL`, `orphanRemoval = true` — deleting a tour deletes its logs)

Schema is generated by Hibernate (`ddl-auto=update`). `Duration` fields (estimated time, total time) are stored as minutes via a custom `DurationMinutesConverter` (a JPA `AttributeConverter`).

## Cross-cutting concern: security & the auth flow

Stateless JWT — the server keeps no session. Walk it through like this:

**Registration/login**
1. `POST /api/auth/register` → `AuthService` checks username/email are free, BCrypt-hashes the password, saves the `User`.
2. `POST /api/auth/login` → looks the user up by username *or* email, verifies the password with `passwordEncoder.matches`, and `JwtService.generateToken` issues a signed JWT (HMAC-SHA, subject = username, 24 h expiry).

**Authenticated requests**
3. The client sends `Authorization: Bearer <token>` on every request.
4. `JwtAuthenticationFilter` (a `OncePerRequestFilter` registered before Spring's `UsernamePasswordAuthenticationFilter`) extracts the token, validates the signature and expiry via `JwtService`, loads the user through `UserDetailsServiceImpl`, and puts an `Authentication` into the `SecurityContextHolder`.
5. `SecurityConfig` says `/api/auth/**` is public and **everything else requires authentication**, with `SessionCreationPolicy.STATELESS` and CSRF disabled (safe here because we use bearer tokens, not cookies).
6. Downstream, services read the authenticated username from the `SecurityContext` to enforce ownership.

Key classes: `SecurityConfig` (filter chain, `DaoAuthenticationProvider`, `BCryptPasswordEncoder` bean), `JwtService` (token mint/parse), `JwtAuthenticationFilter` (per-request auth), `UserDetailsServiceImpl` (loads users for Spring Security, assigns `ROLE_USER`).

## Cross-cutting concern: DTOs and mapping

Every endpoint takes a `...Request` DTO and returns a `...Response` DTO; entities stay internal. Request DTOs carry the bean-validation annotations (`@NotBlank`, `@Min/@Max`, `@Positive`). This means the API contract is decoupled from the database schema and sensitive fields (like `password`) are never serialized out. DTOs use hand-written builder classes; mapping is done in the services today (a recommended refactor is to centralize it in a `TourMapper`).

## Integration layer: OpenRouteServiceClient

When a tour is created/updated without an explicit distance or time, `TourService` asks `OpenRouteServiceClient` to compute them. The client geocodes the `from`/`to` strings to coordinates (`/geocode/search`), then POSTs to `/v2/directions/{profile}` where the profile is derived from the transport type (car→`driving-car`, bike→`cycling-regular`, etc.). It parses distance (m→km) and duration (seconds) out of the JSON. **Graceful degradation:** if the API key is missing or any call fails, it returns sensible fallback values so the app keeps working in a demo.

## Domain logic worth highlighting

Two computed values live on the `Tour` entity as `@Transient` getters (not stored, derived on read):
- **Popularity** = number of tour logs.
- **Child-friendliness** = a 0–100 score combining average difficulty (from logs), estimated time, and distance, each normalized and weighted. It's a nice concrete example of business logic to talk about.

## Request lifecycle, end to end (memorize this one example)

`POST /api/tours` with a JSON body and a Bearer token:
1. `JwtAuthenticationFilter` validates the token, sets the security context.
2. `SecurityConfig` confirms the request is authenticated.
3. `TourController.createTour` runs `@Valid` on the `TourRequest` (400 if invalid).
4. `TourService.createTour` opens a transaction, resolves the current user, maps DTO→`Tour`, calls `OpenRouteServiceClient` to fill distance/time, saves via `TourRepository`.
5. Hibernate INSERTs into `tours`; the transaction commits.
6. The saved entity is mapped to a `TourResponse` and returned as `201 Created`.

If you can narrate that confidently, you can answer most "show me how X works" questions.
